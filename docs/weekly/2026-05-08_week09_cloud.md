# Week09 Cloud Summary｜Docker Desktop + kind Local K8s Rollout

Date: 2026-05-08  
Scope: local Docker Desktop + kind dev cluster only.

## 1. Goal

Week09 focused on verifying local Kubernetes release semantics for the Java service. The goal was to prove that the Java backend can be loaded into a local kind cluster, deployed as a Kubernetes workload, checked through rollout status / history, dry-run rollback, health endpoint, and Prometheus metrics endpoint.

## 2. Verified Scope

This week verified the following local-only evidence:

- Docker context used `desktop-linux`.
- kind cluster `cloud-dev` was used as the local dev cluster.
- Namespace `dev-platform` was used.
- Java backend Deployment `media-task-platform-java` reached `1/1 READY`.
- Local PostgreSQL and Redis dependencies reached `1/1 READY`.
- Kubernetes Service endpoint was observed.
- Rollout status succeeded.
- Rollout history was captured.
- Rollback dry-run was verified.
- Health probe returned HTTP 200 with `{"status":"UP"}` through port-forward.
- Prometheus metrics were captured through `/actuator/prometheus`.

## 4. Evidence Boundary

This week does not verify:

- Real cloud-provider deployment.
- Provider-backed Terraform apply.
- Production rollout.
- Production rollback drill.
- Remote state.
- Production-grade SLO / alerting policy.
- Alertmanager or on-call workflow.

## 5. Week10 Handoff

Week10 should stop deepening local rollout mechanics and move to SLO / alerting draft:

- `docs/runbooks/slo.md`
- `observability/prometheus/alerts.yaml`
- local rule validation using `promtool` or an equivalent Docker-based Prometheus toolchain.

The next hard step is to define local SLI / SLO semantics and encode first-pass Prometheus alert rules without claiming production readiness.
